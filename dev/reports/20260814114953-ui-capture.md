## What is actually being compared

#1055 shipped remote locking. It works: a build on one controller takes a resource that lives on
another, and the console says so. What it did not ship is any way to *see* it. The lockable
resources page of the borrowing controller knew nothing about remote locks, and neither did the
lending controller's.

So this is not a "new feature" comparison. It is the same working feature, before and after it
became visible.

Both sides were photographed in the identical state, driven by the same script: `nightly-hardware-test #1`
holding `hw-rig-01` on `hw-lab`, and `smoke-on-rig #1` queued behind it. Proof from the upstream run's
own consoles:

```
nightly-hardware-test #1  Trying to acquire remote lock on [Resource: hw-rig-01] (serverId=hw-lab, ...)
                          holding hw-rig-01
smoke-on-rig #1           Trying to acquire remote lock on [Resource: hw-rig-01] (serverId=hw-lab, ...)
```

## 2. What the new tab holds

![remote tab](20260814114953-ui-capture/after-remote-own-locks.png)

Both states the table can show, in one shot: the lock this controller holds, and the request still
queued for it. Each row names the server, what was asked for, what came back, and which build asked —
linked, so the row leads somewhere. There is no "before" for this; the information had nowhere to live.

The note is deliberate. This is the client's own record, not the server's, and the page says so
rather than implying an authority it does not have.

## 3. Delegated mode

![delegated](20260814114953-ui-capture/after-delegated-badge.png)

A controller can be configured to send every `lock()` elsewhere. That is a large thing to do
silently, so the page says where the calls go, and says that the local resources listed underneath
are still lockable by others — they are simply no longer used to answer this controller's own calls.

![catalog](20260814114953-ui-capture/after-remote-catalog.png)

Underneath it, what the delegated server publishes: names, status, who holds what, labels. Fetched
on view and cached, with the age of the observation stated.

## 4. Maintenance

![paused](20260814114953-ui-capture/after-paused-banner.png)

Draining a server before taking it down refuses new acquires while leaving held locks alone. Clients
wait instead of failing. The banner says so on the server that is draining, and names the switch to
put it back.

## Global configuration

`before-config.png` / `after-config.png` capture the whole configuration page. They are ~10,000px
tall and worth little as a comparison: #1055 already shipped the remote sections, and this PR adds
exactly two switches to them — *Accept new acquire requests* (`[B3]`) and per-remote *Enabled*
(`[B5]`). The JCasC block in the README covers that ground better than a screenshot can.

## What the capture found

Photographing the UI turned up three defects in this PR's own commits, all fixed and amended into
the commit that introduced them:

| defect | commit | symptom |
|---|---|---|
| `.lr-remote-note` had no CSS | `[C2]` | Jenkins symbols carry an intrinsic 512px size, so the icon rendered at the full width of the page |
| `.lr-delegated-badge` had no CSS | `[C3]` | same, plus no banner layout at all |
| `.lr-paused-banner` had no CSS | `[C4]` | same |
| apostrophe eaten | `[C3]` | `${%key}` goes through `MessageFormat`, where a lone `'` opens a quoted section: "this controller**s** own lock() calls". Fixed with `''` |
| space dropped before `(35s)` | `[C3]` | Jelly trims leading whitespace in a text node; `&#160;` restores it |

None of this is reachable from a diff, a unit test, or an E2E assertion on page content — all three
CSS-less blocks were *present* in the DOM and asserted on. They were only wrong to look at.
